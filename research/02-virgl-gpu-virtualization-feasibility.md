# VirGL / Venus / GFXStream / rvgpu as a uniform GPU-acceleration layer for plain Docker containers

**Question:** Can a "GPU provider container" running virglrenderer (vtest), Venus, GFXStream, or rvgpu give real, production-usable GPU acceleration (OpenGL *and* Vulkan, good enough for Wine+DXVK/VKD3D — Roblox Studio — and Chrome) to *sibling plain Docker containers* (namespaces only, no KVM/hypervisor), as a single mechanism that works uniformly regardless of whether the host GPU is Intel, AMD, or NVIDIA?

**Verdict up front: No — not for real production workloads.** All of virgl/Venus/GFXStream are fundamentally VM-transport protocols designed to cross a *hypervisor* boundary (virtio-gpu device in a KVM/crosvm/QEMU guest). The one part of that stack that *can* run over a plain Unix socket without a VM — virglrenderer's **vtest** server — exists specifically as a *testing/CI harness for virglrenderer itself*, not a hardened multi-tenant production GPU server, and it only carries the OpenGL (virgl) protocol at usable performance; Vulkan-over-vtest (Venus transport `VN_DEBUG=vtest`) is explicitly a developer/CI convenience, not something anyone runs workloads over. rvgpu is architecturally the closest fit (no hypervisor needed) but is built for automotive HMI/compositing, needs privileged kernel modules, and has no real Vulkan story. VirtualGL is real, mature, production-grade, and *does* run today across sibling Docker containers sharing one GPU — but it only forwards GLX/OpenGL, not Vulkan, so it can't carry DXVK/VKD3D traffic at all. In practice, for plain-namespace Docker containers, everyone still just does direct `/dev/dri` (Intel/AMD, via shared Mesa) or NVIDIA Container Toolkit/CDI (NVIDIA) passthrough and accepts the two-mechanism split. That is the realistic recommendation here, not a virgl-based provider container.

---

## 1. virglrenderer's vtest mode

- **What it is**: `virgl_test_server` (aka vtest) is a Unix-domain-socket rendering server bundled with virglrenderer. A client sets `GALLIUM_DRIVER=virpipe` (Mesa's "virgl over vtest" gallium driver) plus, per the Ubuntu manpage, `LIBGL_ALWAYS_SOFTWARE=1` on the client side (this flag disables the *client's own* direct GPU access, not the server's — the client is only serializing GL calls over the socket, so it shouldn't try to open a real DRM device itself). ([Ubuntu manpage](https://manpages.ubuntu.com/manpages/focal/man2/virgl_test_server.29.html))
- **Design intent**: virglrenderer's own docs describe vtest as "a lightweight separation of host hardware and client software that was originally only conceived for testing purposes." ([Mesa VirGL docs](https://docs.mesa3d.org/drivers/virgl.html))
- **Does the server side use real hardware?** Yes, it *can* — the server opens a real GL context on the host via `--use-gles`, `--use-glx`, or `--use-egl-surfaceless`, so if the host has a working Mesa (Intel/AMD/nouveau) or even proprietary GPU driver, rendering is genuinely hardware-accelerated on the server. It is not automatically llvmpipe — llvmpipe only shows up if the host itself falls back to software (e.g., no working GPU driver), same as any other Mesa app. Confirmed in practice by a Waydroid feature request describing exactly this topology (Android-in-LXC → vtest socket → host NVIDIA GPU) — though that issue itself is an unimplemented proposal with **no confirmed working report**, not evidence it's solid. ([Waydroid #564](https://github.com/waydroid/waydroid/issues/564))
- **Vulkan support**: virglrenderer's vtest server can be built with `--venus` to also carry Venus (Vulkan) traffic, and Mesa's Venus (`vn`) ICD has a `VN_DEBUG=vtest` mode that talks to it over the same plain socket instead of a real virtio-gpu kernel device. This *does* prove the Venus wire protocol itself is VM-agnostic at the transport level. But every source describing this frames it purely as a way to test/develop Venus without spinning up a VM — not a deployment target. ([Mesa Venus docs](https://docs.mesa3d.org/drivers/venus.html), search result on `VN_DEBUG=vtest`)
- **Practical reliability**: a real-world bug report (Ubuntu 24.04 regression breaking vtest hardware acceleration for Blender-in-Distrobox that worked on 22.04, closed unresolved/"not planned") shows this path is fragile across distro/Mesa versions with no one actively hardening it for that use case. ([ubuntu-rockchip #941](https://github.com/Joshua-Riek/ubuntu-rockchip/issues/941))
- **Multi-client / concurrency**: no documentation claims vtest is safe/performant for multiple simultaneous heavy clients. The one concrete performance data point in this space (see Collabora below) is that even *inside a real VM*, plain VirGL degrades badly with more than one concurrent OpenGL app — vtest, being the simpler/less-optimized transport, would not be expected to do better.

**Bottom line on vtest**: technically capable of touching real host hardware over a plain socket, but it is a test harness that happens to work, not a supported production GPU server. No project uses it that way for real workloads; the one real container tool that references it (a Rockchip/ARM SBC Distrobox workaround) hit unresolved breakage.

## 2. Venus and GFXStream

- **Venus** (Vulkan command serialization for virtio-gpu) reached "stable" status in Mesa in May 2023 and is genuinely production-quality — but *as a VM technology*. It requires: host Vulkan 1.1 + blob-resource support (available in crosvm, landing in QEMU), and a **guest kernel ≥ 5.16** with virtio-gpu blob/context-init support, because the intended (fast) transport is the virtio-gpu kernel driver talking to a VMM (crosvm/QEMU), not vtest. Tested host drivers: ANV 21.1+, RADV 21.1+, NVIDIA 570.86+, Turnip 22.0+, Lavapipe 22.1+. ([Mesa Venus docs](https://docs.mesa3d.org/drivers/venus.html))
- Its only shipped production consumers are **Android Cuttlefish/emulator** and **ChromeOS Crostini**-style VMs (crosvm) — i.e., always behind a real (micro)VM boundary. Collabora's 2025 state-of-the-art writeup discusses Venus, VirGL, and the newer "vDRM" approach entirely in VM-guest terms; it explicitly calls out that plain **VirGL** ("running more than one OpenGL application in the guest results in a significantly lower performance") has a serious multi-app-concurrency problem, motivating the newer Zink+Venus and vDRM directions — none of which relax the VM requirement, they just improve what happens *inside* one. ([Collabora, "The state of GFX virtualization using virglrenderer," Jan 2025](https://www.collabora.com/news-and-blog/blog/2025/01/15/the-state-of-gfx-virtualization-using-virglrenderer/))
- **GFXStream** (formerly Vulkan Cereal, now merged into Mesa) is Google's code-generated serialization layer for the Android Emulator and Cuttlefish. Cuttlefish plugs gfxstream in through **crosvm's virtio-gpu/rutabaga path** — i.e. still routed through a VMM (crosvm), which itself requires `/dev/kvm`. It is not a hypervisor-free architecture; it just replaces QEMU with the lighter crosvm VMM. ([gfxstream README](https://android.googlesource.com/platform/hardware/google/gfxstream/+/fbc9e43e236777dacf23c0d4bf71dc414df984a9/README.md), [Phoronix](https://www.phoronix.com/news/Mesa-Gfxstream-Merged))
- A related macOS case (Podman Desktop / Red Hat's "AI inference on macOS Podman containers" work) is informative precisely because it shows the *opposite* of what the user wants: to get GPU-accelerated compute into a macOS Podman "container," Red Hat's approach still goes through **libkrun**, which is itself a lightweight hypervisor (uses the Hypervisor.framework) exposing a virtio-gpu device to the guest — i.e., even this "container" workflow secretly is a microVM under the hood. ([Red Hat Developer](https://developers.redhat.com/articles/2025/06/05/how-we-improved-ai-inference-macos-podman-containers))

**Bottom line on Venus/GFXStream**: both are real, actively developed, and reasonably fast — but only across an actual hypervisor boundary (KVM-backed VMM: crosvm or QEMU). Neither is designed to be, or has been used as, a plain-namespace-container GPU server.

## 3. rvgpu (Panasonic/unified-hmi "remote-virtio-gpu")

- Architecture: `rvgpu-proxy` (client side, needs the `virtio-gpu` and `virtio-lo` **kernel modules** loaded, run with superuser privileges) talks over network/socket to `rvgpu-renderer` (server side, does the actual compositing/GL work, built on libvirglrenderer). A `virtio-loopback-driver` kernel module creates virtio devices in userspace without a VM. Secure Boot must be off (unsigned kernel module). ([Panasonic-Automotive/remote-virtio-gpu](https://github.com/Panasonic-Automotive/remote-virtio-gpu), [virtio-loopback-driver](https://github.com/unified-hmi/virtio-loopback-driver))
- This is genuinely the *closest architectural match* to "one GPU-provider process serving multiple client processes/containers without a VM": `rvgpu-renderer` explicitly supports multiple concurrent `rvgpu-proxy` clients compositing into one output, and there is Docker packaging (`unified-hmi`/`ucl-tools`) for it.
- But: it's built for automotive **infotainment/HMI display compositing** (Wayland output via `rvgpu-wlproxy`/Weston), not headless high-throughput 3D/Vulkan workloads. No documentation surfaced mentions Vulkan support (it rides on libvirglrenderer, i.e. the OpenGL/virgl protocol) — same ceiling as plain VirGL, including the multi-client performance concerns noted above. It also demands loading unsigned privileged kernel modules on the host, which is arguably a *heavier* operational burden than simply mounting `/dev/dri` — it doesn't avoid needing host-level, kernel-level setup, it just relocates it into different modules.

**Bottom line on rvgpu**: real, working, non-VM, but scoped to automotive display compositing, OpenGL-only, no evidence of Vulkan or of being used for demanding interactive 3D apps like games, and no lighter on host privilege requirements than the alternative you're trying to avoid.

## 4. Prior art check: Crostini, Waydroid, "GPU server in Docker"

- **ChromeOS Crostini** = crosvm + virtio-gpu + virglrenderer + Sommelier (Wayland proxy). Confirms the general component shape (one GPU-serving process, Wayland-forwarded output to multiple guest apps) — but again, crosvm is a real VMM requiring KVM. Useful as a mental model, not as evidence this works without a hypervisor.
- **Waydroid** uses an LXC container (genuinely non-VM) for Android, and *does* use `/dev/dri` passthrough by default for GPU access (shared Mesa driver, same DRM kernel subsystem) — its only virgl-related GitHub issue is an **open, unimplemented feature request** for NVIDIA (which lacks a usable open DRM render-node path the way Intel/AMD do), not a working deployment. This is a good illustration of the actual industry pattern: containers use direct `/dev/dri` when it's available (open drivers), and only reach for virgl-ish workarounds for the one vendor (NVIDIA, or oddball ARM/Mali setups) where direct passthrough doesn't cleanly work.
- **Distrobox** (genuinely plain, unprivileged-capable Linux containers) is the strongest real-world precedent found, and it validates the *opposite* of the virgl idea: "AMD GPUs work through Mesa with no special flag... Intel GPUs work the same way... Blender inside a container will use the host GPU through the shared driver" — i.e., Distrobox's actual, working, default mechanism for Intel/AMD is **direct `/dev/dri` bind-mount + shared host Mesa userspace driver**, not virgl/vtest. Its NVIDIA story is a `--nvidia` flag that shares the host's proprietary driver stack into the container (same idea as NVIDIA Container Toolkit). virgl/vtest only showed up in this research as an ARM-SBC-specific workaround (Rockchip Mali) — and that specific case was reported broken/regressed and closed unresolved.
- No credible, maintained project was found that runs a virglrenderer/vtest/Venus process as a general-purpose "GPU render server" fanning out to multiple sibling Docker containers for real desktop/gaming workloads. Every serious production reference either (a) is VM-bound (Crostini, Cuttlefish, libkrun/macOS), or (b) just does direct device passthrough per container.

## 5. VirtualGL (distinct technology, flagged as requested)

- VirtualGL is unrelated to virtio-gpu/virgl: it's an X11 GLX command-interposition library. A GPU-owning "VirtualGL server" runs the real (typically Xorg-driven, often headless via Xvfb/EGL) GL context, and client apps' GLX calls are intercepted and forwarded to it, with rendered frames read back and composited into the client's own X display (locally or over VNC/Sunshine/TurboVNC).
- This is mature, widely deployed, and genuinely used today to **share one GPU across multiple sibling Docker containers** — real setups exist (`nvidia-xorg-virtualgl-docker`, `plumbee/nvidia-virtualgl`, Steam-Headless/Kasm-style images use `Xvfb` + `vglrun`). `vglserver_config +s +f +t` is the standard way to open 3D X access to all users/containers on a box. ([nvidia-xorg-virtualgl-docker](https://github.com/didzis/nvidia-xorg-virtualgl-docker/blob/master/README.md), [plumbee/nvidia-virtualgl](https://github.com/plumbee/nvidia-virtualgl), [DZone: Hardware-Accelerated OpenGL Rendering in a Linux Container](https://dzone.com/articles/hardware-accelerated-opengl-rendering-in-a-linux-container))
- Its ceiling: **GLX/OpenGL only.** It cannot carry Vulkan traffic, and DXVK/VKD3D (which is how Wine gets acceptable D3D9-12 performance today, and what Roblox Studio would realistically run through) are Vulkan-based. VirtualGL would be irrelevant for that workload; it could theoretically matter only for a pure-OpenGL wined3d fallback, which is far slower and not what anyone wants for Roblox Studio.
- Also worth noting: some real-world reports (`VirtualGL/virtualgl#193`) describe a single-GPU multi-`vglrun` contention bug where a later job's `vglrun` can knock over an earlier one — so even VirtualGL's "share one GPU across many processes" story has rough edges under concurrent real load, not a fully solved problem either.

## Conclusion / Recommendation

For the user's actual goal — one uniform mechanism to give Wine+DXVK/VKD3D (Roblox Studio) and Chrome real GPU acceleration inside several **plain Docker containers**, across hosts that are Intel, AMD, or NVIDIA:

- **virgl/vtest, Venus, and GFXStream are VM-transport technologies.** The one non-VM escape hatch (vtest) is an upstream-acknowledged testing/CI harness, carries only OpenGL at usable quality (Vulkan-over-vtest is a dev convenience, not a deployment path), has at least one documented real-world regression, and no evidence of anyone running real interactive/gaming workloads through it in production.
- **rvgpu** is the one genuinely non-VM "GPU provider process" architecture found, but it's scoped to automotive display compositing, OpenGL-only, and needs privileged/unsigned kernel modules — no lighter than the passthrough it would replace, and no Vulkan.
- **VirtualGL** is production-grade and does let multiple sibling containers share one GPU today — but it's GLX/OpenGL-only and structurally cannot carry the Vulkan traffic Roblox Studio via DXVK actually needs.
- **What people actually do**, confirmed by Distrobox's real (non-VM, unprivileged-capable) container GPU story: bind-mount `/dev/dri` and share the host's Mesa userspace driver directly for **Intel/AMD** (this part genuinely *is* uniform across those two vendors — same DRM/Mesa stack, same env vars, no version pinning headache), and use **NVIDIA Container Toolkit/CDI** to inject the matching proprietary userspace driver for **NVIDIA** hosts. That's two mechanisms, not one, but both are mature, well-documented, low-overhead, and near-native performance — unlike anything in the virgl/venus/rvgpu family for this use case.

**Recommendation**: drop the virgl/venus "uniform GPU provider container" idea for this project. Implement host-detection in the compose/entrypoint tooling that picks between (a) `/dev/dri` device passthrough + `video`/`render` group membership for Intel/AMD hosts, and (b) NVIDIA Container Toolkit/CDI for NVIDIA hosts. That is the real "uniform enough" answer available today — a single detection branch, not per-host hand-tuning, but still two code paths under the hood rather than the single virgl-socket abstraction the user was hoping for.
